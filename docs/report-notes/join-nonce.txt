Join nonce: each client accepts only the answer to its own JoinRequest
=====================================================================

The problem (baseline, still there after #14)
- Every JoinResponse goes to every client (one topic, no addressing). Each
  waiting client took the first response it saw, so two clients waiting at the
  same time both took the first answer and played as the same player.
- The server could not tell a repeated request from a new client. A client
  whose response was lost (or late) asked again 1 s later and was given a
  second slot; the first slot stayed filled by nobody ("ghost"). With 5 slots,
  a few ghosts fill the game.
- The baseline server also passed requests to the main thread through one flag
  and one stored ID, so requests arriving together were merged into one.

What changed (2026-10-28, on top of #14)
- Client (client/net_client.c): picks a random non-zero 64-bit nonce once
  (getrandom, net_random_nonce() in common/net.c), sends it in every
  JoinRequest, and accepts only the JoinResponse with the same nonce; up to
  JOIN_TAKE = 8 responses are taken per call and the others dropped.
- Server (server/lobby.c, net_server.c): the DDS worker queues every request's
  nonce (up to JOIN_QUEUE = 16); the main thread answers each in order and
  remembers the nonce with the slot. A nonce that already holds a slot gets the
  same slot again, so repeats never fill a second one. Every answer (JOIN_OK
  or JOIN_FULL) carries the request's nonce.
- Nonce 0 (a client without a nonce) is never matched to a slot.
- FUSE_JOIN_NONCE=off (server and clients) keeps the baseline join: nonce 0,
  first response taken, every request a new slot (the "before"; same binaries).
- No change to the steady state: JoinRequest/JoinResponse already carried the
  8-byte nonce field (sent as 0) since #12, and only the join path changed, so
  the normal-play profile (opt-14-qos) still applies; not re-profiled.
- Security plan (PLAN.md section 3): "each nonce is accepted once" holds in
  the sense that a nonce can never get a second slot; a repeated (or replayed)
  request gets the same answer again. Once the login is added, that answer's
  session key is protected so that only the real client can read it.
- Leave was not done at this point: a slot (and its nonce) was never freed
  (see leave-timeout.txt for the next step).

How it was measured (bench/join_loss.sh, headless clients bench/dds_joiner.c)
- Server + 4 headless clients per trial, each staying 10 s, 10 trials per cell,
  loopback dropping 0 / 10 / 30 % of packets (tc netem). Modes:
  qos = #14 QoS with FUSE_JOIN_NONCE=off (before), nonce = #14 QoS + nonce.
- Clients started 1.5 s apart (as for #14): bench/results/join-nonce-loss/
- Clients started at the same instant (the race): bench/results/join-nonce-simultaneous/

What this shows
1. With the nonce, no two clients ever share an ID and no slot is ever filled
   twice, in every case (0 of 240 joined clients; 0 ghosts). Without it, 4
   clients starting together end up mostly on the same IDs (30 of 40 hold a
   duplicate even with no loss), and the server fills 11-14 slots nobody
   uses.
2. "Joined" and "join_ms" before the nonce flatter the baseline: a client that
   took someone else's response counts as joined, often before it even sent
   a request (requests per client 0.53: it took the response meant for the
   client that asked first, so join_ms = 0). Those joins are wrong.
3. Join time with the nonce is the real round trip: 17-21 ms for 4 clients
   arriving together (the server handles them in one pass, then the worker's
   20 ms polling sleep), 2 ms for one client alone.
4. Under 30 % loss, join times have two groups: under 500 ms (the first
   exchange, or a reliable resend, gets through) and 1 s or more (the client
   had to wait for its 1 s retry). The share under 500 ms was 24/40, 24/40 and
   22/40 (#14) in three runs and 16/40 in the staggered nonce run, which moves
   the median from ~300 ms to 1003 ms. The simultaneous nonce run (24/40,
   median 199 ms) shows the nonce itself does not slow joining; more trials
   would be needed to tell 16/40 from 24/40 reliably.
5. The one client that did not join (simultaneous, 30 %, trial 2) sent 9
   requests and the server only ever had 3 players, so none of its requests
   arrived: most likely DDS discovery between it and the server kept losing
   packets. Not a nonce problem.

Testing
- DDS test tool against the server: nonce 111 -> player 1, again -> player 1;
  3 different nonces written together -> 3 different players; 5th player OK;
  6th nonce -> JOIN_FULL with its nonce; a joined nonce repeated while full ->
  its own slot. All pass; with FUSE_JOIN_NONCE=off they fail as the baseline
  would (repeat -> new slot, game fills up).
- Tick/movement test (sends nonce 0, i.e. an old-style client) still passes.
- Two real clients started at the same instant: banners "Player 1" and
  "Player 2"; with FUSE_JOIN_NONCE=off both show "Player 1".
