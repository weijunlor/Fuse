## Findings so far

- Cyclone DDS security plugins on Ubuntu 24.04 (WSL) are in `/usr/lib/x86_64-linux-gnu/libddsc0debian/`, not the default library path. Check the path again on other machines.
- Baseline client uses ~300% CPU in WSL: uncapped rendering (no vsync), busy-looping DDS worker, likely llvmpipe software rendering threads.
- TSan does not report the `int_player_id` race at runtime (the main thread locks the same mutex every frame, so the single write is almost always ordered). Treat it as a code-review finding, not a TSan result.
- WSL2 usually lacks hardware perf counters; use native Ubuntu for cache/branch/IPC numbers.
- Native Ubuntu 26.04 laptop (i7-14650HX, P-cores = CPUs 0-15, E-cores 16-23): README packages plus `pkg-config` are needed. Ubuntu's perf has no BPF, so `perf lock contention -b` fails; use `perf lock record` and then `perf lock contention -i`. Kernel symbols need `kptr_restrict=0`; tracepoint files are root-only, so `bench/profile.sh` runs perf lock/trace with sudo (the user must have set paranoid/kptr/governor first; ask them).
- `perf lock contention` (tracepoints) sees kernel locks only, not pthread mutexes. Baseline user-space mutex contention shows as futex syscalls in `perf trace -s`: server main thread 7.3M and DDS worker 11.3M futex calls in 30 s (~620k/s). Use the futex count as the "before" for #1–3.
- Client GL renderer on the native laptop is zink (OpenGL on Vulkan) on NVK, RTX 4060. Mesa has no symbols, so `bench/render.sh` reports perf samples per thread and library. The desktop is Wayland at 133% scaling: the 800x600 window has a 1066x800 framebuffer (the client sets the viewport to it).
- #16a at 10000 sprites: batched uses 7.6x fewer instructions per frame but no less time, because 82% of samples are one `memmove` in libc called by the driver, copying the client-side vertex array (10000 x 4 x 16 B = 640 KB/frame) at under 1 GB/s. #16b (8-byte vertices) halved it; next is a vertex buffer object (#16c).
- Particles (`bench/results/opt-0[567]-particle-*`): the naive AoS is held back by cache misses and branches only when it has holes or is larger than cache (25% full at 1M: 740 vs 1 LLC misses per 1000 updates, 3.2x slower than SoA). With the pool full and in cache, SoA's scalar gain is small (1.3x); the big win from the layout is that it lets the loop vectorise. GCC only vectorises the clamp loop with `-fno-trapping-math`. SSE2 to AVX2 gains only ~1.1-1.2x because the loop is limited by L2/memory bandwidth (IPC falls to ~2). The worker pool costs ~6-10 µs per tick (two barriers): slower than 1 thread up to ~10k particles, faster from 100k (8 threads: 2.7x at 100k, 4.4x at 1M). The first serial swap-remove did not scale (the main thread moved lines that worker cores had just written), so removal is done per chunk in parallel and only the gaps are closed serially.
- Client CPU depends on input, not on the screen: an idle client uses ~1.0 CPU because its DDS worker busy-polls when no key is held; a moving client (MOVE=1) uses ~0.015 because the worker sleeps 10 ms per pass and the render thread is held to vsync by the compositor (~0.008 CPUs, `perf stat --per-thread`). Earlier notes blaming screen blanking for 0.015 were wrong.
- The client also sends ~120 messages/s to the Wayland compositor (Unix socket, GL thread); `profile.sh`'s net step counts only UDP fds (saved in `raw/net_*_udpfds.txt`). Baseline join race: clients waiting for a join at the same time all take the first JoinResponse and get the same player ID (fixed by the join nonce; reproduce with `FUSE_JOIN_NONCE=off`).
- Packet loss on loopback for tests: `sudo tc qdisc add dev lo root netem loss 10%`, remove with `sudo tc qdisc del dev lo root` (`bench/join_loss.sh` does both). Cyclone's traffic between local processes goes over `lo`.
- Cyclone default QoS: writers RELIABLE, readers BEST_EFFORT, both KEEP_LAST 1. A reliable reader never matches a best-effort writer (test tools must ask for best-effort on Input/GameSnapshot).
- `--input-send every-10ms` clients send nothing while idle, so the server times them out after 5 s and they rejoin: idle "before" runs of #13 need `FUSE_LEAVE=off`.
- Tests that `pkill -x server` also kill a server the user started by hand (and a second server on the same DDS domain answers joins too): check `pgrep -a -x server` first.
- Baseline server CPU use is bimodal: 8 of 10 runs ~1.19 CPUs, 2 runs ~0.79. Report per-run values, not just mean ± stddev.
